ABSTRACT
Network traffic analytics have increased in relevance as researchers promoted machine learning techniques
to tackle several traffic management challenges. Over the past decade, the research community and the
networking industry have investigated, proposed, and developed a growing number of solutions. However, a
large subset of proposed approaches is based on unreliable measurement tools and methodologies. Additionally,
some findings are reported on private datasets, which results in a lack of applicability and reproducibility. This
paper covers the design and implementation of NFStream, a flexible network data analysis framework. Its key
features are flexibility, real-time statistical analysis, and the ability to provide reliable ground truth for modern
network usage. NFStream provides the community with a common research framework that can help stimulate
research in this field and develop more efficient, reproducible solutions.

2. NFStream highlights
NFStream is an open-source framework that allows high throughput
network traffic flow analysis to be run on commodity hardware. The
flows are being formed by aggregating packets that share a common
key. A seven-tuple currently defines this flow key: the source and
destination IP addresses and port numbers, and the protocol, VLAN, and
tunnel identifiers. (If tunnel decoding is deactivated, only a six-tuple is
used with no tunnel identifier in the flow key.) Traffic information, such
as flow features (e.g., the total number of bytes of all packets belonging
to a particular flow) and the flow key – also often referred to as flow
properties – is carried in NFStream in flow entries. Flow features are
derived from the IP, TCP, and UDP packet headers. Their computation
involves analysis-centric methods, such as determining the statistical
summary (minimum, maximum, mean and standard deviation) of the
packet length and inter-arrival time, TCP flags accounting or the early
sequence of packets dynamics (sizes, directions and inter-arrival time).
Besides flow statistics calculation, NFStream can also determine
the types of applications that generate the flows. This feature – also
often referred to as application awareness – is achieved by integrating
the nDPI [23] library. nDPI is a ntop [6] maintained superset of the
popular OpenDPI library. It detects protocols at the application layer,
regardless of the port being used. Furthermore, nDPI can also handle
encrypted traffic via its built-in decoder for SSL (both client and server)
certificates. nDPI can work even when no complete packet payload
is available. Truncating packet payloads is a common technique in
monitoring operational network traffic. Because of storage space constraints and privacy reasons, only a limited portion of packet payloads
are exposed to the sniffers. NFStream enables accurate traffic flow
classification on an application layer since it can handle such cases
via nDPI, implying its applicability not only in unsupervised but also
supervised ML use cases.
NFStream was designed to operate on both live and offline modes
and rely on libpcap, the de facto standard library used for packet
capture. High-speed live network traffic measurement is achieved via
parallelism, specifically via a modified version of libpcap that supports
AF_PACKETv3 (a socket in Linux that allows an application to receive
and send raw packets) and allows load balancing packets across several
cores on Linux systems. On platforms not supporting AF_PACKETv3,
NFStream implements flow-aware hash-based dispatching that runs in
both online and offline modes.
Tunneled traffic is typically composed of different flows, but these
flows might be organized into one flow from a measurement point
of perspective. Decoding tunneled traffic is not an obvious task to

3. High-level description
Fig. 1 depicts the overall architecture of NFStream composed of
2 main components: NFStreamer and a set of parallel Meters. In what
follows, we briefly describe the main functions of these components.
3.1. Packet observation
The packet observation layer is destined for observing packets from
both online and offline traffic capture. This layer is implemented in C
and bound to Python using C Foreign Function Interface (CFFI) [29],
an interface that allows the interaction with almost any C code from
Python, to avoid bottleneck issues. This implementation choice allows for performing several packet-related processes efficiently while
exposing a unique NFPacket Python object.
1. Packet capture is enabled on the network interface card level.
After passing various checksum error checks, the packets stored
in on-card reception buffers are moved to the hosting device
memory. Several libraries are available to capture network traffic. The most popular is perhaps libpcap destined for UNIX-based
operating systems, and winpcap for Windows. NFStream implements a modified version of libpcap library that is used for both
online and offline modes.

2. Packet truncation is destined for selecting precise bytes from
the captured packet (e.g., snapshot length). It is also used to
reduce the amount of data captured, which leads to reduced CPU
and bus bandwidth load.
3. Packet timestamping is a mandatory functionality as packets
may come from several observation points. NFStream relies
on software packet timestamping, which provides milliseconds
accuracy.
4. Packet filtering serves packet filtering based on a set of characteristics. A packet is selected if the specific fields are equal
or in the range of the given values. NFStream packet filtering
is based on the Berkeley Packet Filter (BPF) syntax. BPF provides a kernel-based interface to the link and network layers.
It possesses features that make it highly efficient at processing
and filtering packets [30]. A user-mode interpreter for BPF is
provided with the libpcap implementation of the pcap API,
so programmers can write applications that transparently support a rich set of constructs to build detailed packet filtering
expressions for network protocols.
5. Packet processing consists of a set of parsers that allow NFStream to decode the packet and extract its attributes as part of
NFPacket object, which is the shared object between the packet
observation layer and the metering layer of each meter process.
An overview of these attributes is provided in Table 1.
6. Packet dispatching consists of load balancing packet processing
across parallel meters. As stated above, this feature is implemented via the Linux kernel using the AF_PACKETv3 feature.
However, both online mode and offline modes require a load
balancing in userspace. NFStream achieves such a task by computing a flow-aware hash for each packet. If the computed hash
matches the meter identifier, the packet is consumed. Otherwise,
it is used only as a time ticker.

2. Expiration management runs on top of three flow termination
logics. The first one is active expiration and terminates a flow
that is active during a predefined period. The second is referred

during a predefined period. The last logic represents a custom

3. NFPlugins are a set of NFPlugin, which is a user-defined extension of NFStream. An NFPlugin is instantiated by using a
flexible set of keyword arguments, including specific parameters or external data required for the flow feature computation
(i.e., trained model, externally loaded C library).
The flow metering process calls each NFPlugin defined by the
user at mainly three flow existence stages: initiation, update,

and expiration. Thus, an NFPlugin defines a method called for
each stage. on_init method is called for creation with the first
packet belonging to it. on_update is triggered each time a new
NFPacket is mapped to the flow entry. Finally, on_expire is
performed when at entry is considered as expired. Consequently,
extending NFStream is simple. Adding new flow features or
ML model outcomes can be achieved in just a few lines. Listing 1 demonstrates such a scenario where a trained ML object
(i.e., trained scikit-learn model object) is evaluated in realtime. For brevity, in this example, we suppose that the model
was trained based on per-flow bidirectional bytes and packet
counters.

TiE [33] is a noteworthy solution, however, its ground-truth development is based on unreliable methods. Specifically, it utilizes labeling
introduced by Moore and Papagiannaki [34] extended with CoralReef
and L7-filter that were shown to perform poorly in determining application classes [35,36]. Additionally, the integration of ML classifiers
relies on a different platform (e.g., Weka [37]). Moreover, it also lacks

and shown to perform reliably [38]. Furthermore, NFStream integrates
ML effectively via its platform-independent NFPlugin that, besides ML
integration, also makes it highly extensible with new features. Lastly,
the superiority of NFStream over TiE is also manifested in its quality of
being an open-source solution.
Most open-source flow metering tools do not provide performance
indicators. Even though it is specified in cases, it is usually a performance indicator of what the developers achieved on test systems
rather than a guaranteed performance [39]. This is mainly because the
performance of flow meters strongly depends on several factors such
as the number of packets to be processed, the volume of flows, and
the performance and capabilities of the underlying system (i.e., CPU,
memory, storage technology, and network interface card). Parallel processing also significantly impacts performance, although multi-thread
(CPU) processing of the captured packets is not common to see among
existing open-source solutions. Lastly, the number of calculated flow
features (statistics) and their computing complexity (requirements) also
heavily impact the processing time.
The latter two factors exceptionally hindered the comparison of
NFStream to popular solutions such as YAF [2], pmacct [3], CAIDA
CoralReef [4], SoftFlowd [5], and nProbe [6]. These tools can calculate a significantly lower number of flow features and, in doing so,
provide flow measurement only at a coarser granularity. Additionally, these solutions are in close conformity with the NetFlow/IPFIX

metering processes and the definition of the flow export format. Thus,
working with flow-based data is as simple as instantiating a single class.

pandas format came as natural as it is the de facto standard input

The obtained results are depicted in Fig. 2 and demonstrate a significant
speed gain when running NFStream on top of PyPy vs. CPython.
In scenarios 1 and 2, the average speed gain of PyPy vs. CPython
was around 34%. Tunnel decoding and determining application types
(ground truth) seem to have little to no impact on top of the core
functionality demands of NFStream. In scenarios 3 and 4, the speed
gain is lower. With only one CPU core involved in the processing, the
average speed gain was around 30% in scenarios 3 and 4, while with
two CPU cores, the gain dropped to around 23%. Interestingly, the
lowest speed gain of PyPy vs. CPython was achieved using 4 CPU cores,
specifically around 17% in scenario 3 and around 11% in scenario 4.
However, neither the activation of statistical features nor splt features
or anonymization have a significant overhead on the processing time
of NFStream. Our results showed only around a 9% increase of all
features activated vs. only core features. Overall, PyPy has a positive
impact on the operation of NFStream. CPython compiles the Python
code into bytecode and interprets it within the evaluation loop, which
results in less efficiency than other compiled languages. In contrast,
PyPy leverages Just In Time (JIT) compilation (translating a subset of
Python code into fast machine code) leading to significant performance
gain. NFStream also leverages CFFI bindings helping to improve its
performance further. It is noteworthy that the performance overhead
and demands can be reduced further by selecting only a subset of
discriminators (features) required for a particular use case.

can be implemented in just a few lines of code.
4.1. NFStream Performance Indicators
An unbiased comparison with existing solutions is undoubtedly
complex and prone to various factors that can distort actual efficacy.
Nonetheless, we performed a benchmark of processing times across
multiple parameter settings to give a grasp on NFStream’s performance.
To this end, we organized the packets of a pcap file into flows using
the default configuration of NFStream and stored the obtained flow
entries in a CSV file (cf. Listing 2). The pcap used for the benchmark
was captured at an average-sized European university network. The
average traffic rate of the measured uplink was around 1.60 Gbps. The
capture duration of the traffic trace is 299 s, and it contains 62 M
packets with complete payloads. The data byte and bit rates of the trace
are 165 MBps and 1320 Mbps, respectively, with an average packet
size of 795.35 bytes and an average packet rate 207 kpackets/s. It
is noteworthy that the monitored network has not reached its typical
traffic rate due to the COVID-19 pandemic.

4.2. Scholarly Publications Enabled by NFStream
The popularity of NFStream is characterized by a steady increase.
Castaneda Herrera et al. [43] developed a novel approach for identifying video streaming services in 5G Networks. The flow records
classified via supervised machine learning (including Logistic Regression, KNN, Naive Bayes, and Regression Tree) are obtained using
NFStream. Liu et al. [44] proposed a lightweight hybrid form of IDS —
an embedded model for feature selection and a convolutional neural
network for attack detection and classification. Using NFStream, the
Authors collected and developed the CCD-INID-V1 dataset, whose traffic was captured at the Center for Cyber Defense, North Carolina A&T
State University. Bikmukhamedov and Nadeev [45,46] introduced a
neural network framework that allows constructing multi-class network
traffic models suitable for flow generation and classification tasks.
During the evaluation, they utilized NFStream to assign flow labels
and extract packet features from pcap files. Sun et al. [47] proposed a
deep learning approach to detect malware using data collected from a
web crawler that systematically sent requests to benign and malicious
websites on the Internet. NFStream was used to perform traffic flow
analysis. The work was developed as part of a research project aimed
at enhancing the defensibility of network systems against malware, AIbased cyber attacks, and other security threats. Jonsson and Edeby [48]
analyzed Tor network traffic that reveals what data is sent through the
network. The data collected using NFStream at three Tor exit nodes
(US, Germany, and Japan) helped drawing conclusions about Tor usage.
Finally, Pekar et al. [49] studied four publicly available traffic traces
(UNIV1, UNIV2, CAIDA2016, and CAIDA2018) and provided useful
insights and suggestions on how to determine more justified and valid
thresholds for heavy-hitter network traffic flow detection. The traffic
traces were processed and organized into flow records using NFStream.
5. Conclusion
This paper introduced NFStream, an open-source network data
analysis framework. Its parallel processing capabilities, online and
offline traffic processing modes, application awareness, flexibility, and
straightforward path from networking to ML make NFStream viable
among existing open-source solutions. By leveraging the tool, research
outcomes can become more natural to reproduce, comparable against
other studies, and generalizable to other systems that have not been
studied yet.
While the obtained results are promising, our work revealed both
challenges and space for improvements. We actively work on increasing
the performance and flexibility of NFStream. We plan to extend its
support for Microsoft Windows operating systems. We also consider the
implementation of high-speed packet capture frameworks, such as Intel
DPDK [50]. Finally, a consistent effort will also be put into dataset
development. We believe they can provide an excellent incentive for
much broader adoption of both ML/AI and reproducibility.
